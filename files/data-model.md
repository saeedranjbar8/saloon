# مدل داده (پیش‌نویس ۱)

نام جدول‌ها انگلیسی است چون در کد می‌آیند. این سند با `booking-rules.md` هماهنگ نگه داشته می‌شود.

## پایه
- `cities`: شهرها.
- `users`: موبایل، هش رمز، نام، جنسیت، تاریخ تولد، نقش (athlete / manager / office)، وضعیت (فعال / تعلیق‌شده).
- `sports`: رشته‌های ورزشی، قابل مدیریت توسط اداره.
- `holidays`: تعطیلات از داده.
- `settings`: مقادیر قابل تغییر اداره (مدت قفل، سقف رزرو در انتظار، ...).

## سالن و برنامه
- `venues`: شهر، نام، آدرس، امکانات، وضعیت.
- `venue_managers`: پیوند کاربر و سالن.
- `bookable_units`: هر سالن حداقل یک واحد دارد (برای بخش‌های نادر).
- `unit_sports`: رشته‌های هر واحد.
- `schedule_templates`: روز هفته، شروع، پایان، طول سانس.
- `schedule_exceptions`: تعطیلی و بستن سانس.
- `slots`: سانس‌های مشخص (واحد، شروع، پایان) که از قالب تا ۳۰ روز جلو ساخته می‌شوند.
- `price_rules`: قیمت هر رشته در هر بازهٔ زمانی، با تاریخچهٔ تغییر.

## رزرو و پول
- `bookings`: سانس، کاربر (برای رزرو دستی خالی)، منبع (online / manual)، رشته، وضعیت، نوع تغییر وضعیت (manual / auto)، قیمت تعرفه و مبلغ واقعی (ریال)، مهلت قفل، اطلاعات رزرو دستی (نام، شماره، روش دریافت).
- `payments`: مبلغ، شناسهٔ درگاه، وضعیت، کلید یکتا برای جلوگیری از تکرار.
- `refunds`: مبلغ، وضعیت، علت.

## کیفیت و نظارت
- `reviews`: یک نظر برای هر رزرو، امتیاز، متن اختیاری، وضعیت (visible / hidden)، نشان تأییدنشده برای رزرو خودکار.
- `complaints`: کد رهگیری، شاکی، دسته، سالن مرتبط، توضیح، وضعیت.
- `complaint_notes`: یادداشت‌ها و پاسخ‌های اداره.

## داده و ثبت‌ها
- `events`: نوع، عامل، موجودیت، جزئیات، زمان. خوراک تحلیل و حسابرسی.
- `access_log`: هر بازکردن اطلاعات شخصی توسط اداره.
- `sms_log`: ارسال و خطا.
- اسکیمای تحلیل (جدا): ویوهای تجمیعی مثل اشغال روزانهٔ هر سالن، بدون اطلاعات شخصی. داشبورد اداره از اینجا تغذیه می‌شود.

## قیدهای دیتابیس
- سانس‌های یک واحد هم‌پوشان نباشند (exclusion constraint).
- برای هر سانس حداکثر یک رزرو فعال (در انتظار یا تأییدشده).
- کلید یکتا برای هر پرداخت.
- یک نظر برای هر رزرو.
- مبالغ عدد صحیح (ریال). زمان‌ها با منطقهٔ زمانی (Asia/Tehran برای نمایش).
- قید ضدهم‌پوشانی باید در migration به‌صورت SQL نوشته شود، مستقل از ORM.

## فاز ۲ و داده‌های ورزشکار
- برای قابلیت‌های فاز ۲، سابقه رزرو و وضعیت پرداخت/بازپرداخت قابل بازیابی باشد؛ رسید PDF از داده تراکنش و رزرو ساخته می‌شود و الزام به نگهداری فایل PDF نیست.
- علاقه‌مندی‌ها به رابطه کاربر و سالن نیاز دارند؛ پروفایل و تغییر رمز از داده کاربر/احراز هویت استفاده می‌کنند.
- مرزبندی فازها نباید حذف زیرساخت رزرو، پرداخت یا احراز هویت فاز ۱ را القا کند.

## تصمیم‌های باز
- سیاست کاربران زیر ۱۸ سال و تعارض رزرو کل سالن با بخش‌ها همچنان تعیین نشده‌اند.
